2. Introduction

In contemporary financial markets, rapid asset price fluctuation requires investors and portfolio managers to maintain real-time situational awareness over their capital allocations. Traditional single-threaded financial tracking software frequently suffers from severe performance degradation under production conditions: sequential network requests to remote financial endpoints induce high cumulative latency, freezing user interfaces during periodic refreshes. Furthermore, non-synchronized in-memory state models expose multi-threaded applications to critical data race conditions, phantom updates, and dirty reads.

The Multi-Threaded Stock Portfolio Tracker is an industrial-grade, framework-free Java 17 application architected from first principles to solve these challenges. By decoupling user interaction from asynchronous background polling through high-performance concurrency primitives—specifically ScheduledExecutorService, dedicated worker thread pools, and concurrent memory structures—the system delivers sub-millisecond local menu responsiveness alongside continuous real-time market data ingestion. Furthermore, by pairing a resilient JDBC persistence layer (supporting zero-configuration SQLite and scalable MySQL) with strict financial arithmetic (BigDecimal), the project guarantees precision, high concurrency throughput, and proactive multi-channel alerting.

3. Problem Statement

Retail investors and software engineers face several foundational difficulties when designing equity tracking software:

  • Compounding Network Latency in Sequential Polling: Querying remote financial REST APIs sequentially scales network latency linearly (O(N)), causing severe delays and frequent HTTP socket timeouts as portfolio sizes expand.
  • Data Race Hazards in Concurrent State Access: Concurrently mutating portfolio valuations from background ingestion threads while simultaneously rendering them on user threads leads to severe race conditions, dirty reads, and ConcurrentModificationException crashes.
  • Floating-Point Arithmetic Inaccuracy: Primitive binary floating-point types (float, double) cause IEEE-754 precision loss in cumulative financial valuations, resulting in inaccurate profit/loss (P&L) calculations.
  • Lack of Automated Multi-Channel Alerting: Passive portfolio monitoring requires continuous manual inspection. Without an automated alerting subsystem tracking volatility thresholds, rapid market drawdowns go unnoticed.
  • Brittle External Dependencies: Systems that crash when an API key is missing or when rate limits are exceeded cause unacceptable downtime and loss of portfolio visibility.

4. Functional Requirements

The system provides three major functional modules with explicit input/output structures and workflows:

4.1 Module 1: Portfolio & Holding Management

  • FR-1.1 (Add Holding): Allows users to add stock positions with ticker symbol, company name, purchased quantity, and average buy price.
  • FR-1.2 (Strict Input Validation): Enforces uppercase alphabetic validation (1–5 characters) for tickers, capitalizes company names, mandates positive numbers for quantities/prices, and cleanly handles EOF streams.
  • FR-1.3 (Remove Holding): Removes existing positions from memory and cascades deletions to the database store.
  • FR-1.4 (Tabular Reporting): Renders aligned ANSI terminal tables displaying Symbol, Company Name, Quantity, Buy Price, Current Price, Current Value, Unrealized P&L ($), and Percentage Return.

4.2 Module 2: Asynchronous Real-Time Market Data Ingestion

  • FR-2.1 (Live REST Ingestion): Integrates with Alpha Vantage's GLOBAL_QUOTE REST endpoint via standard Java 11+ HttpClient and Jackson Databind.
  • FR-2.2 (Parallel Multi-Worker Fetch):** Executes quote retrievals for distinct symbols concurrently across an isolated fixed thread pool (ExecutorService).
  • FR-2.3 (Scheduled Periodic Refresh): Triggers automated refresh cycles at configurable intervals (e.g., 60 seconds) using a daemon ScheduledExecutorService.
  • FR-2.4 (Offline Fallback): In the absence of an API key or during network downtime, seamlessly retrieves and serves last-known valid prices from the local database.

4.3 Module 3: Alert Engine & Concentration Risk Analysis

  • FR-3.1 (Dynamic Thresholds): Enables runtime configuration of global and per-symbol percentage change thresholds.
  • FR-3.2 (Multi-Channel Dispatching): Dispatches alerts simultaneously to the console terminal, an append-only audit file (alerts.log), and the relational alerts_log database table.
  • FR-3.3 (Duplicate Alert Suppression): Caches the last-alerted price per ticker to eliminate redundant alerts during flat or fluctuating sideways trends.
  • FR-3.4 (Concentration Risk Assessment): Evaluates equity weightings and proactively warns users if any single holding exceeds 40% of total portfolio value.

8. Design Decisions & Rationale

  • Core Java Concurrency vs. Spring Boot: Spring Boot wraps concurrency behind high-level annotations (@Async, @Scheduled). By explicitly building with ScheduledExecutorService, ExecutorService, and explicit monitor locks, the architecture demonstrates transparent, deterministic control over thread lifecycles.
  • Decoupled Clock and Worker Pools: Using a single timer thread to directly execute HTTP calls causes timer drift and thread starvation. Delegating network requests into a separate 5-thread worker pool isolates scheduling precision from external latency.
  • Hybrid ConcurrentHashMap and Synchronized Compound Operations: While ConcurrentHashMap permits concurrent reads, atomic multi-field state updates (e.g., computing portfolio aggregates while price updates execute) necessitate method-level monitor locks.
  • BigDecimal Precision: Financial applications must never use IEEE-754 binary floating-point numbers (double, float). BigDecimal with RoundingMode.HALF_UP guarantees exact cent and percentage precision.
  • Defensive Snapshots for Iteration: getSymbols() returns an unmodifiable defensive copy of the ticker set, preventing concurrent modification errors if positions are added/deleted while quotes are refreshing.

12. Challenges Faced & Solutions

  • Handling Stream EOF Without Silent Defaults: Previously, Scanner stream closure defaulted quantities to BigDecimal.ONE. This was refactored to return null, cleanly aborting the transaction with a "Cancelled." prompt.
  • Strict External API Quota Management: Alpha Vantage's 25 requests/day limit was addressed via persistent DB caching; the app runs smoothly in offline mode when limits are hit.
  • Preventing Concurrent Modification During Asynchronous Iteration: Iterating over live ConcurrentHashMap key sets while positions are added/removed was secured by exposing immutable snapshot sets.
